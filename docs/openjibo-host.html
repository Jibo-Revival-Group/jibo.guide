OpenJibo: Replacement Cloud

OpenJibo is the active community replacement-cloud track. It is rebuilding the robot-facing API, notification sockets, and higher-level runtime so a revived Jibo can use a hosted or self-hosted service. It is substantial and usable, but it is not a claim that every original cloud feature is complete.

ℹ️ Current managed endpoints

The documented managed path uses api.openjibo.com for the robot-facing API, open-jibo-socket.openjibo.com for notification traffic, and neohub.openjibo.com for the NeoHub/listen path. A local server uses your own hostnames or controlled DNS instead.

⚠️ Hosting is not the same as retargeting

Starting a server does not make a stock robot connect to it automatically. The robot still needs a software configuration change, controlled DNS/hosts routing, and TLS that the device accepts. The eMMC recovery in Route A gives you the write/SSH path; endpoint conversion is a separate, image-specific step. The Tegra fuse remains a boot-signing identity lock, not a cloud-hostname lock.

For a first local test, use the current .NET implementation. The Node server is valuable as a protocol oracle, but it is not the long-term production path.

2. Install the local server

EZJiboServer is the community installer. It installs the required toolchain, clones OpenJibo, creates local configuration and certificates, and leaves run.sh and update.sh in ~/EZJiboServer. Inspect downloaded scripts before executing them on your machine: 

$ cd ~
$ curl -fsSL https://raw.githubusercontent.com/Jibo-Revival-Group/EZJiboServerGit/refs/heads/master/setup.sh -o ezjiboserver-setup.sh
$ less ezjiboserver-setup.sh
$ bash ezjiboserver-setup.sh

The installer is currently documented and tested primarily on Arch Linux and Ubuntu. It may also detect other package managers, but check its output and make sure the required .NET/PowerShell/OpenSSL dependencies are available.

3. Run the server locally

The local mode is the best way to verify that the server starts before involving a robot. It uses file-backed local persistence and does not need root or port 443: 

$ cd ~/EZJiboServer
$ ./run.sh local

In another terminal, check the HTTP health endpoint:

$ curl http://localhost:24605/health

The helper pulls the latest OpenJibo checkout before starting. To test the already installed checkout without pulling, use NO_UPDATE=1 ./run.sh local. Stop it with Ctrl-C.

4. Run a physical-device endpoint

Live/device mode binds HTTPS on port 443, which is the port expected by the stock robot-facing clients. Use certificate material that the robot's routing and trust setup accepts; the generated self-signed certificate is intended for the controlled setup documented by OpenJibo, not arbitrary public deployment: 

$ cd ~/EZJiboServer
$ CERT_PEM=/path/to/cert.pem KEY_PEM=/path/to/key.pem ./run.sh live

Port 443 may require elevated privileges. Do not run live mode while another local server is using that port. For the robot side, follow the current OpenJibo device-bootstrap notes: they describe region-driven configuration, the notification suffix, native compatibility hostnames, and the image-specific TLS requirements. Keep a full robot-specific eMMC dump before experimental conversion writes.

What is supported today?

  • OpenJibo hosted/local cloud: active replacement-cloud work with a current .NET implementation and a legacy Node protocol oracle/capture harness. The OTA update flow is detailed in the upstream OpenJibo server repository and should be trivial to recreate for interested developers. OTA-assisted recovery and broader OS conversion remain active work, not a universal one-click flow.
  • OOBE-first OTA: a promising bootstrap candidate under test, not yet a universal replacement for the RCM/SSH recovery path.

Read the upstream OpenJibo living documentation before changing endpoint, region, native-library, or TLS files on a robot.
