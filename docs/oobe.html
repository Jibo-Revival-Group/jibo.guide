Out-of-Box Setup (OOBE)

When you first powered on a brand-new Jibo, he walked himself through a short setup sequence — show a logo, ask to be plugged in, scan a QR code off your phone, connect to WiFi, and download his first update. Jibo engineers called this the Out-Of-Box Experience, or OOBE.

Understanding OOBE matters for one blunt reason: a stock, un-modded Jibo can no longer finish it against the original service. The production cloud it tries to reach was shut down in 2019, so setup stops partway through. This page explains what the robot is trying to do, where it gets stuck, and how the current recovery and replacement-cloud paths differ.

ℹ️ Where this happens on the robot

A factory Jibo ships in a locked-down state called oobe mode. In this mode almost nothing runs — no skills, no open ports — except a single setup app called oobe-config, which launches automatically on boot and drives everything below.

The three things Jibo must do

Setup is really a loop that won't let go until all three of these succeed. If any one fails, Jibo shows an error and starts over:

  1. Get on WiFi — join your home network.
  2. Register with the cloud — prove he belongs to your account and receive his own login credentials.
  3. Run the first update (OTA) — pull down the current software.

Only after all three does he switch into normal mode, reboot, and wake up as the Jibo you know.

Step by step

1. The QR code carries everything

When you tapped "Set Up a New Robot" in the Jibo phone app, the app generated one or more QR codes and Jibo read them with his camera. That QR code isn't just your WiFi name — it's a bundle (lightly scrambled) containing:

  • Your WiFi SSID and password
  • Optional static-IP settings (IP, netmask, gateway, DNS)
  • A one-time access token tied to your app account

Jibo uses the first part to join WiFi, and holds onto that access token for the next step.

2. Registering with the cloud

Now online, Jibo phones home. He hands the cloud his one-time token plus his factory name (the four-word identity like castle-cylinder-fig-quilt) and asks to be set up. In return the server gives back a permanent access key and secret key, which Jibo saves to his own storage.

This is the moment a robot becomes yours: the token proves which account asked for setup, so the server attaches the robot to your "loop" (your Jibo household) and issues the credentials he'll use for every future cloud request. Without this exchange, Jibo has no identity and cannot talk to any server function.

3. First update, then wake up

With credentials in hand, Jibo asks the update service what packages he needs, downloads them, and installs them. Finally oobe-config flips the robot from oobe mode to normal mode and reboots. In normal mode Jibo runs his main personality skill (Be) on boot — his eye appears, and he's alive.

What the robot was pointed at

The robot keeps a tiny config file naming which server "region" to use (production robots used prod-entrypoint). That short name expands into the actual addresses Jibo tried to reach:

PurposeAddress (production)
Account / setup / updates (REST API)https://prod-entrypoint.jibo.com
Live notifications & Commander (WebSocket)wss://prod-entrypoint-socket.jibo.com

Behind those two addresses sat the whole Jibo backend — the account, loop, robot, update, and notification services. All of it went offline when the company wound down.

Why a stock Jibo gets stuck

⛔ The dead end

When Jibo reaches step 2 and calls prod-entrypoint.jibo.com to register, nothing answers. The "register with the cloud" gate never closes, so the setup loop never completes. The robot sits on the connecting/searching screen and retries indefinitely. There is no menu, no skip, no offline option — OOBE was built on the assumption that the cloud would always be there.

This is the single reason thousands of otherwise-healthy robots are silent. The hardware is fine. The software is intact. It's just waiting on a handshake with a server that no longer exists.

🔒 One more catch: fusing

The Tegra fuse is not a lock to a cloud hostname. It locks the boot/signing identity of a fused robot. Every unit has the fuse circuitry, but a particular robot may be unfused, developer-fused, or production-fused; the archived engineering documentation describes the fuse as a physical one-way change to the signing identity.

The old supported stack-switch workflow was restricted for production-fused units, which is the source of much of the earlier wording. ShofEL2 is a different layer: it gives the owner a raw eMMC/NAND read-write path, so software configuration such as the server target can be changed without changing the physical fuse. This bypasses the normal OS/OOBE access path, not the Tegra's cryptographic boot-signature checks; it does not unfuse the robot or make an unsigned boot image valid.

See the archived pvindex fuse notes and server-stack notes.

On an SSH-capable image, the archived check is cat /sys/devices/platform/tegra-fuse/odm_production_mode: 0x00000001 means fused and 0x00000000 means unfused. For a fused unit, developer-versus-production identity is established by which signed build it accepts; a nonzero public-key field alone is not the test.

How the revival gets past OOBE

Rather than try to satisfy a dead cloud, the recovery mod in this guide takes the robot out of oobe mode entirely. By dumping Jibo's storage and editing his software mode setting (the mode.json change in the manual route), we switch him into an internal developer mode that boots with SSH access and does not run the setup handshake. This is a software-mode change, not a fuse conversion.

From there, the things the cloud used to provide are replaced locally, on your own network — no jibo.com required:

  • SSH & Next Steps — get a root shell and choose compatible community software
  • Skills Service Manager — start the Be skill so Jibo comes to life
  • Local ASR — on-device speech recognition, no cloud
  • Re-Commander — control head, speech, camera, and an LLM voice loop from your browser
ℹ️ Recovery mode and server targeting are separate changes

The recovery step edits /var/jibo/mode.json to obtain developer mode and SSH. Pointing a revived robot at a replacement service is a later configuration task: depending on the stack and image, it can involve the Jetstream region settings, server-service notification suffix, credentials, and TLS/native compatibility. It is not a hardware-fuse conversion or necessarily a one-line URL edit. Follow the current OpenJibo device instructions for the exact image-specific files.

ℹ️ Replacement-cloud status

Yes: the community has reverse-engineered enough of the original protocol to run replacement services. OpenJibo is the active hosted/local replacement-cloud track, with robot-facing API, socket, and NeoHub endpoints; its protocol oracle/capture work and OTA-assisted recovery are still evolving. The OTA update flow is detailed in the upstream OpenJibo server repository and should be trivial to recreate for interested developers. The archived pvindex OTA notes document the historical package, target/filter, and version-matching behavior.

This does not mean that entering a server URL alone completes every stock OOBE step. The current repeatable recovery path is still RCM/ShofEL2 followed by SSH. An OOBE-first OTA bootstrap is under active test and may eventually reduce that work, but it is not yet a universal, zero-touch procedure.

A Note on OOBE Robots

⚠️ OOBE-first OTA is still a candidate path

If your Jibo has never completed OOBE — meaning he still boots into the setup/connecting screen rather than his eye — he is stuck in oobe mode. Do not assume that the current OpenJibo hostname or a hand-edited URL will make stock setup complete: OOBE also expects the historical registration, credentials, update-manifest, TLS, and time-handling behavior.

OpenJibo documents a promising OOBE-first OTA bootstrap under test, including emulated setup/update endpoints and signed-by-manifest assets. Until that path is repeatable for your image, the dependable owner-recovery route is the RCM/AutoMod path, followed by SSH and a deliberate choice of OpenJibo, BEam, or another compatible community stack.

Follow the community's OpenJibo device-bootstrap notes and join the Discord for image-specific instructions. Preserve a full robot-specific dump before experimental writes.
