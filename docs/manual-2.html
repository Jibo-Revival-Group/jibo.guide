Route B — Step 2: Dump & Modify the eMMC

With Jibo in RCM mode and ShofEL2 built, you'll now dump the eMMC storage, extract the /var partition, and change the software mode setting that enables developer access. This does not change the Tegra's physical fuse state.

⚠️ Keep Jibo in RCM mode the entire time

Jibo must stay plugged in and in RCM mode throughout this step. Do not press any buttons on Jibo or unplug the USB cable until instructed.

Part 3 — Dump the Full eMMC

Run ShofEL2's EMMC_READ command to dump the entire eMMC storage to a file. This takes 2–4 hours and produces a file of approximately 15 GB. 

$ cd ~/JiboAutoMod/Shofel
$ sudo ./shofel2_t124 EMMC_READ 0x0 0x1D60000 full_jibo_dump.bin
ℹ️ If it crashes at 98–99%

A read that stops near the end is not a complete backup, regardless of the percentage shown. Check that the GPT and the complete partition 5 are readable; otherwise re-enter RCM and re-run the read. If you only need developer mode, use AutoMod's --mode-json-only fast path instead. Never label a truncated image as a restorable full-eMMC backup.

✅ Keep your backup

Once the requested read completes, copy full_jibo_dump.bin to external storage or another machine. This file contains your Jibo's unique calibration data — it cannot be recovered from another Jibo. A partial read is not a substitute.

Part 4 — Find the /var Partition

Use fdisk to list the partition table inside your dump file and identify the /var partition (partition 5, approximately 500 MB): 

$ fdisk -l full_jibo_dump.bin

You'll see output like this:

Disk full_jibo_dump.bin: 14.68 GiB, 15757999104 bytes, 30777342 sectors
Units: sectors of 1 × 512 = 512 bytes

Device                   Start      End  Sectors  Size Type
full_jibo_dump.bin1         34  2048033  2048000  1000M Microsoft basic data
full_jibo_dump.bin2    2048034  4096033  2048000  1000M Microsoft basic data
full_jibo_dump.bin3    4096034  4198433   102400    50M Microsoft basic data
full_jibo_dump.bin4    4198434  8294433  4096000     2G Microsoft basic data
full_jibo_dump.bin5    8294434  9318433  1024000  500M  ← This is /var
full_jibo_dump.bin6    9318434 30777310 21458877  10.2G Microsoft basic data

Note down the Start and End sectors for partition 5. The values below are only an illustration; never use them if your GPT reports different values.

ℹ️ Example values (yours may differ slightly)
  • Start: 8294434
  • End: 9318433

Part 4a — Extract the /var Partition

Calculate the sector count: (End − Start) + 1 

(9318433 - 8294434) + 1 = 1,024,000

Then extract the partition with dd (use your Start and Count): 

$ dd if=full_jibo_dump.bin of=var_partition.bin \
    skip=8294434 count=1024000

Make a backup of the original before modifying it:

$ cp var_partition.bin var_partition_backup.bin

Part 4b — Mount and Edit mode.json

Mount the partition image as a loop device and navigate to the config file: 

$ mkdir -p jibo_var
$ sudo mount -o loop var_partition.bin jibo_var/
$ cat jibo_var/jibo/mode.json

You'll see:

{"mode": "normal"}

Change "normal" to "int-developer":

$ sudo nano jibo_var/jibo/mode.json
# Or use any editor: vim, gedit, vscode, etc.

The file should now contain exactly:

{"mode": "int-developer"}
🚨 Unmount before writing back

You must unmount the loop device to flush all writes to var_partition.bin before the next step. Skipping this will result in a corrupted partition image. 

$ sudo umount jibo_var
ℹ️ What does int-developer mode do?

Switching to int-developer mode changes the software boot mode, disables the developer-mode firewall rules, and enables additional services, including SSH on port 22. It does not alter the hardware fuse or its boot-signing identity. The normal boot animation is replaced by a large checkmark, which confirms the mode was applied successfully.

Continue to the next step to flash the modified partition back to Jibo.
